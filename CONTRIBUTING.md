# Contributing to OpenWork

OpenWork welcomes technical and nontechnical contributions. We're currently planning the platform, so thoughtful feedback and documentation are useful contributions too.

## Ways to help

- **Engineering:** Architecture research, development, integrations, tests, security reviews.
- **QA and accessibility:** Test plans, usability feedback, acceptance criteria, accessibility reviews.
- **Product and design:** User research, workflows, design proposals, inclusive interfaces.
- **Documentation:** Clear writing, onboarding, tutorials, translations.
- **Community:** Identify genuine problems, help newcomers, review project proposals, mentor when possible.

## Start here

1. Read the [README](README.md), [ROADMAP](ROADMAP.md), and [Code of Conduct](CODE_OF_CONDUCT.md).
2. Search [existing issues](https://github.com/openwork-community/openwork/issues) before suggesting a new idea.
3. Open an issue that describes the problem, who benefits, your proposed approach, and how you could help.
4. Wait for agreement on scope before starting large work. Once development begins, we'll document local setup and tests.

You don't need organization membership to contribute via public issues or pull requests. Please never put personal contact details, private résumés, access tokens, or sensitive reports in public issues.

## Proposing a feature or community project

A strong proposal explains: **problem**, **intended users**, **evidence the need is real**, **smallest useful solution**, **possible contributor roles**, **long-term maintenance**, and **privacy/security risks**.

Use the [project-proposal issue template](.github/ISSUE_TEMPLATE/project-proposal.md) when available. Submitting a proposal doesn't guarantee approval or volunteer staffing.

## Pull requests (once implementation begins)

- Link work to an agreed issue; prefer small, reviewable changes.
- Explain the change, motivation, and how it was tested.
- Include accessibility considerations and screenshots for UI changes when relevant.
- Only submit work you have the rights to license under Apache-2.0.
- Never commit secrets, unlicensed assets, or private user information.
- Respond to feedback constructively; maintainers review changes before merging.

Technology-specific style, setup, testing, and release instructions will be added after the stack is chosen.

## Crediting real work

Contributors may reference their actual public work in their portfolios or job applications. Participation does not imply an employment relationship, internship, certification, referral, or guaranteed job.

## Community norms

Please follow the [Code of Conduct](CODE_OF_CONDUCT.md). We want beginners to feel comfortable asking questions and experienced contributors to provide useful feedback.
